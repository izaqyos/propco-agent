# Known limitations and how I'd fix them

Five real limitations of the current build, each a deliberate scope cut for a home assignment rather than an oversight, with the concrete next step to remove it.

1. **A cached degraded answer outlives the outage that caused it.** `router` and `extractor` catch `LLMUnavailableError` internally and return a normal (non-raising) result with `degraded=True`; the node-level `CachePolicy` on those two nodes has no concept of "this was a fallback," so it caches the rule-based result for the full one-hour TTL. If Gemini has a two-minute outage on a given question, that question replays the plainer, rule-based phrasing for up to an hour after the provider recovers — the numbers stay correct, only the prose quality degrades silently. Fix: either skip the cache write when `degraded=True`, or give degraded results a much shorter TTL (seconds, not an hour) so a healthy provider is retried soon.

2. **State does not survive a restart or a second process.** `MemorySaver` and `InMemoryCache` are per-process and in-memory: an in-flight clarification is lost if the app restarts, and a second app instance behind a load balancer would not share pending clarifications or cached routes with the first. This was a deliberate choice for a single-instance Streamlit deployment. Fix: swap to `PostgresSaver` (checkpointer) and a Redis-backed cache — `AssetManagerService.__init__` already accepts both as constructor overrides, so this is a config change at the call site, not a graph rewrite.

3. **The rule-based fallback is English-only.** When the LLM is unreachable, `rule_route`/`rule_extract` take over using keyword regex — built and tested against English phrasing only. A Dutch question during an outage degrades to a much weaker, partially-blind rule match rather than a clean templated answer. Fix: either add a minimal Dutch keyword table to `llm/rules.py` (cheap, covers the demo's own Dutch example), or detect non-English input up front and have the degraded-mode message say plainly that fallback routing doesn't cover it yet, rather than silently guessing.

4. **No memory across separate questions.** Every call to `ask()` builds a fully fresh `AgentState` (`graph/state.py::initial_state`); the checkpointer only bridges a single clarification's pause-and-resume, not a whole conversation. "And last quarter?" as a follow-up to a prior question gets no context — the user has to restate the property/period. Fix: seed `initial_state` from the previous turn's resolved filter when the new question looks like a follow-up (e.g., starts with "and", has no explicit period/property of its own) — an opt-in, resolver-level heuristic, not a blanket carry-over, since blindly reusing state would break the data-policy toggle and multi-topic chats.

5. **Contribution vs net is a sentence, not a UI cue.** Property-level P&L excludes entity-level overhead (mortgage interest, management fees) and is labelled *contribution*; portfolio-level P&L includes it and is labelled *net*. That distinction is disclosed in the answer's prose and in the user guide, but the headline `st.metric` card just says "P&L" either way — someone skimming only the big number could compare a contribution figure to a net one without reading the sentence underneath. Fix: label the metric itself (`"P&L (contribution)"` vs `"P&L (net)"`) so the caveat survives even when the prose is skipped.
